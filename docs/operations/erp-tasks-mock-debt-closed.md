# Мок-долг задач закрыт: статус «В работе» и виджет дашборда

Статус: сделано (02.09.2026)

Хвост работы из [erp-tasks-live-api.md](erp-tasks-live-api.md): там реестр задач
переехал на Platform API, и в разделе открытых вопросов остались два пункта.
Оба закрыты.

## 1. Статус «В работе» нельзя было поставить

`in_progress` появился в схеме задачи 02.09.2026 вместе с расширением модели под
экран ERP. Экран показывает четыре состояния, «В работе» среди них — но
`UpdateTaskDto` объявлял `@IsIn(['open', 'cancelled'])`, и попасть в этот статус
задача не могла никак. Статус существовал только на бумаге.

Добавлен в `PATCH /tasks/:taskId`, в OpenAPI и в сгенерированный `api-client`.

**`completed` туда не добавлен намеренно.** Завершение — отдельная команда
`POST /tasks/:taskId/complete`: она пишет `completedAt`,
`completedByPositionId` и событие `TaskCompleted`. Разрешить `completed` в
`PATCH` значило бы завести второй путь завершения, который ничего этого не
делает. Закреплено тестом: `PATCH` со статусом `completed` отвечает 400.

### Побочный эффект, который пришлось починить в том же месте

`hasOpenNextAction` у лида считался по `status: 'open'` — и в
`countOpenForLead`, и в батч-запросе `distinctLeadIdsWithOpenTask`. Пока
`in_progress` был недостижим, это работало. Как только статус стал доступен,
правило превратилось бы в ловушку: **менеджер берёт задачу в работу — и лид
теряет признак «есть следующее действие»**, то есть попадает в список
запущенных ровно в тот момент, когда им занялись.

Введена константа `UNFINISHED_TASK_STATUSES = ['open', 'in_progress']`, обе
выборки переведены на неё. Это не косметика: без этой правки добавление статуса
само по себе создало бы ложные срабатывания правила CRM-003.

## 2. Виджет «Следующие действия» показывал мок

`WidgetNextActions` собирал список из настоящих лидов и просроченных задач из
`TASKS_MOCK` — выдуманное действие стояло в одном списке с настоящими и
визуально от них не отличалось. Теперь просроченные задачи приходят из
`GET /tasks`, просрочку определяет сервер (`isOverdue`), отбор идёт по позиции
из серверной сессии. При отказе сервера виджет говорит об этом строкой и не
подставляет мок.

Заодно удалён проп `currentUserId`: он был id человека из старой CRM и
использовался только для отбора задач. Мёртвая цепочка снята до
`DashboardWorkspace`.

`src/data/tasks-mock.ts` больше не импортируется нигде.

## Найдено попутно: нестабильный тест

`developmentManagementV2Page.test.ts` («StrictMode: initial
publication_pending…») падал примерно в половине параллельных прогонов с
`expected 2 times, got 1`. Гонка: значок «pending» появляется уже после
initial-fetch, а тест сразу требовал два запроса — второй (первый polling-тик)
под нагрузкой не успевал. Проверка обёрнута в `waitFor`; смысл сохранён — если
запросов станет четыре, равенство двум не наступит и `waitFor` упадёт по
таймауту. Пять полных прогонов подряд зелёные.

Тест не мой, но нестабильность вылезла из-за моих двух новых файлов: они
добавили параллельной нагрузки и сделали гонку заметной.

## Проверено

Все три уровня, как требует [architecture.md](../architecture.md) («Изменил
HTTP-контракт — прогони все три уровня»):

- unit API: 82 сьюта, 791 тест;
- интеграционные API: 36 сьютов, 419 тестов (в задачах +5: `in_progress`,
  завершение взятой в работу задачи, отказ `PATCH` завершать, признак
  следующего действия у лида поодиночке и в списке);
- клиент ERP: 33 файла, 199 тестов (+4 на виджет).

Runtime E2E локально не гонялся: изменение контракта чисто расширяющее —
в enum добавлено значение, ни один существующий запрос не становится
невалидным. Playwright-гейт закрывает его на PR.

Шесть мутаций проверены намеренной поломкой кода, все шесть тесты ловят:
недоступный `in_progress`, разрешённое завершение через `PATCH`, признак
следующего действия только по `open`, подстановка мока при отказе, клиентский
пересчёт просрочки в виджете, показ чужих задач как своих.

Два unit-теста репозитория пришлось обновить: они закрепляли `status: 'open'`
буквально — то есть закрепляли ровно то поведение, которое оказалось неверным.
