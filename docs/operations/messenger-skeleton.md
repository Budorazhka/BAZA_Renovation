# Messenger: каркас диалогов без транспорта (этап 10, не начат по DoD)

Дата: 11.09.2026. Код — `80534a3` (10.09), коммит подписан «production-grade».
Статус: каркас. Модель диалогов, прав и привязки к CRM есть. Сообщения никуда не
уходят и ниоткуда не приходят.

## Что сделано

- Модуль `apps/api/src/modules/messenger`: аккаунты (Telegram-бот, WhatsApp),
  диалоги, сообщения, привязка диалога к лиду, контакту или сделке, задача из
  диалога, отметка прочтения.
- Маршруты под `/messenger`: `accounts` (список, подключение бота, подключение
  WhatsApp, удаление), `dialogs` (список, карточка, сообщения, отправка текста и
  медиа, `read`, `link-crm`, `create-task`).
- Все запросы фильтруются по организации. Аудит на операциях с аккаунтами и
  `link-crm`, outbox в транзакции, `Idempotency-Key`, ответы с `id`.
- Права — permission-matrix §1.6.

## Почему это не этап 10

Этап 10 мастер-плана: «серверное подключение каналов и безопасное хранение
provider credentials», модель доставки, in-app и Telegram-уведомления, realtime.
Ничего из этого нет:

- `MessengerMessageSent` стоит в `ACKNOWLEDGED_ONLY_EVENT_TYPES` воркера
  (`apps/worker/src/handlers/handlers.module.ts`): событие подтверждается без
  исполнения. Сообщение при этом сразу получает `status: 'sent'`
  (`messenger.service.ts:422`, `:505`) — система говорит «отправлено», хотя
  отправки не было.
- Входящих нет: вебхуков нет, `dialogRepository.create` не вызывается ни одним
  путём. Диалог в системе появиться не может.
- Аккаунт получает `authStatus: 'authenticated'` сразу при создании
  (`messenger-account.repository.ts:40`). Токен бота не проверяется через
  Telegram, у WhatsApp учётных данных нет вовсе.
- ERP-экран чатов (`apps/erp-web/src/pages/modules/ChatsPage.tsx`) ходит в старый
  отдельный сервис через `messengerApi.ts` и `MESSENGERS_API_URL`. Новый API к
  интерфейсу не подключён.

## Что открыто

1. **Честный статус до появления транспорта.** Не писать `sent` без отправки:
   статус `queued` или «канал не подключён», и видимая пометка в интерфейсе.
2. Транспорт: подключение Telegram Bot API и выбор провайдера WhatsApp —
   решение владельца, затем вебхуки, доставка, повторы.
3. `botToken` хранится открытым текстом без `select: false`
   (`messenger-account.schema.ts:40`): попадает в любой `find` и дамп базы. В ответы
   API сейчас не попадает.
4. Own-scope не применяется к изменениям: `ownerFilterForAction` вызывается только
   для чтения, не для отправки, `link-crm` и `create-task`. Менеджер может писать
   в чужие диалоги и перепривязывать их. Карточка диалога без
   `assignedPositionId` открыта любому менеджеру.
5. `link-crm` не проверяет, что лид, контакт или сделка принадлежат организации и
   зоне видимости вызывающего, и не принимает `expectedVersion`.
6. Вложения: `assetId` не сверяется с организацией, `url` — любая строка.
7. Курсор списка диалогов фильтрует по `_id`, а сортировка идёт по закреплению и
   времени последнего сообщения: страницы теряют и дублируют диалоги.
8. Расхождения с OpenAPI: списки диалогов и сообщений отдают массив вместо
   `{items, nextCursor}`; `link-crm` отвечает 201 вместо 200.
9. Отметка прочтения меняет данные, но защищена правом `read`. Удаление аккаунта
   не удаляет его диалоги.
10. `create-task` использует ту же операцию идемпотентности `createTask`, что и
    `POST /tasks`: один ключ на двух эндпоинтах даст 409.
11. Организации, созданные до 10.09, не имеют грантов messenger: новые гранты не
    доливаются в существующие должности.
