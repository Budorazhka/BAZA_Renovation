# Истечение броней по сроку (N-01)

Дата: 11.09.2026. Статус: сделано; расписание — в compose-профиле `scheduled`,
по умолчанию не поднимается.

## Что было

Бронь не истекала вовсе. `convertToDeal` лишь отказывал в переводе просроченной
брони, а сама она оставалась `pending` или `booked`, юнит — `reserved`. Публичная
проекция берёт только `available`, поэтому юнит навсегда пропадал с витрины.
Этап 7 мастер-плана требует «бронирования с транзакционным conflict lock и
истечением».

## Что сделано

- `BookingsService.expireOverdueBookings({ now?, limit? })` находит брони
  `pending`/`booked` с `dateRange.expiresAt <= now` по всем организациям, пачками
  по курсору `_id`, и истекает каждую в своей транзакции:
  1. `BookingLock.bumpForUnit` первой записью (ADR-006), как у `book()`: истечение
     и новая бронь того же юнита не проходят одновременно.
  2. CAS `expireIfOverdue`: бронь всё ещё `pending`/`booked` и её срок всё ещё
     истёк. Бронь, которую менеджер продлил между выборкой и транзакцией, не
     истекает.
  3. Юнит освобождается (`reserved` → `available`), если на нём не осталось
     другой активной брони.
  4. События `BookingExpired` и, если юнит освобождён, `UnitStatusChanged` —
     по нему воркер пересобирает проекцию ЖК, юнит возвращается в каталог.
  5. Аудит `booking.expire` от системного актора.
- Точка входа `apps/api/src/jobs/booking-expire.command.ts`, скрипт
  `pnpm --filter api run bookings:expire-overdue`.
- Сервис `booking-expire` в `infrastructure/compose/compose.runtime.yml`, профиль
  `scheduled`, интервал `BOOKING_EXPIRE_INTERVAL_SECONDS` (по умолчанию 300 с):

  ```bash
  docker compose -f infrastructure/compose/compose.runtime.yml --profile scheduled up -d
  ```

  Без compose — cron рядом с приложением:

  ```cron
  */5 * * * * cd /srv/baza-platform && pnpm --filter api run bookings:expire-overdue >> /var/log/baza/booking-expire.log 2>&1
  ```

- Частичный индекс `dateRange.expiresAt` только по `pending`/`booked`: выборка не
  сканирует архив.
- Воркер подтверждает `BookingExpired` без побочного эффекта
  (`ACKNOWLEDGED_ONLY_EVENT_TYPES`), чтобы событие не уходило в `dead_letter`.

## Заодно исправлено

- **Освобождение юнита при отмене.** Логика вынесена в общий `releaseUnitIfFree`
  для отмены и истечения. Отмена читала юнит вне транзакции и не проверяла
  `modifiedCount`: если между чтением и записью юнит менялся (пакетное изменение
  цен поднимает `version`), CAS молча не срабатывал — бронь отменена, юнит навсегда
  `reserved`. Теперь юнит читается в снимке транзакции, промах CAS откатывает
  транзакцию целиком (`VERSION_CONFLICT`).
- **Резервирование в `book()`** — та же ошибка в обратную сторону: бронь
  создавалась, а юнит оставался `available` на витрине. Исправлено тем же
  способом; юнит, проданный между проверкой и транзакцией, теперь тоже
  отклоняется.
- **ts-node-команды не компилировались с 03.09.** Импорт лидов добавил в
  контроллер `req.isMultipart()`/`req.file()`, а их типы регистрирует только
  `main.api.ts`. `pnpm run actuality:expire-overdue` и `migrate:legacy-leads` падали
  на TS2339. Compose этого не видел: он запускает скомпилированный `dist`. Во все
  три команды добавлен side-effect импорт `@fastify/multipart`.

## Почему так

Тот же паттерн, что [протухание актуальности](actuality-expire-schedule.md):
операция вызывается командой, расписание живёт в инфраструктуре, в коде нет
scheduling-зависимостей. Интервал 5 минут, а не час: бронь держит юнит часы или
дни, и лишний час в `reserved` после срока заметен покупателю. Прогон дешёвый — по
частичному индексу.

## Проверено

- Юнит-тесты: истечение (освобождение, другая активная бронь, CAS вернул null,
  ошибка одной брони, откат при промахе CAS, пагинация), отмена и резервирование
  через CAS в транзакции.
- Интеграционные на реальной Mongo: истёкшая бронь → `expired`, юнит `available`,
  события и аудит, повтор ничего не меняет; незаистёкшая не трогается; юнит
  остаётся `reserved`, пока есть другая активная бронь; один прогон проходит все
  организации. В тест отмены добавлена проверка статуса юнита — раньше её не было.
- Живой прогон `ts-node src/jobs/booking-expire.command.ts` на полном AppModule
  против Mongo в памяти: `{"expiredCount":1,"releasedUnits":1,"errors":0}`, в базе
  бронь `expired`, юнит `available`. Так же прогнана починенная
  `actuality-expire.command.ts`.

## Что открыто

- **Интервал не согласован с владельцем.** 5 минут — разумный дефолт, не решение
  по продукту.
- **Что происходит с лидом.** Бронь истекла — лид остаётся на своей стадии, задача
  менеджеру не создаётся. Нужно ли уведомление или задача «бронь истекла» —
  решение владельца; точка для этого — обработчик `BookingExpired` в воркере.
- **Нет метрики и алерта.** Ненулевой `errors` несколько прогонов подряд виден
  только в логах.
- **Параллельные прогоны** безопасны — BookingLock и CAS не дадут истечь одной
  брони дважды, — но блокировки на уровне расписания нет.
- Отдельная задача: сейчас юнит `reserved`, пока на нём есть **любая** активная
  бронь, включая будущую непересекающуюся. Юнит с бронью на следующий месяц не
  виден на витрине уже сегодня. Так было и у отмены; правило — решение владельца.
