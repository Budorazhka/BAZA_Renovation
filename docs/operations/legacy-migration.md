# Перенос данных старой системы (N-03)

Дата: 11.09.2026. Статус: **заготовка**. Переносятся только лиды (с 03.09).
Пользователи, организации, объявления и ЖК — нет: нет копии старой базы, и её
схема не обследована. План переезда целиком — вне репозитория
(`docs/codex/plans/2026-09-10-baza-migration.md` в рабочей папке), backlog
MIG-01…MIG-11.

## Что есть

- **Лиды.** `export-legacy-leads.script.ts` (read-only выгрузка из
  `api-crm.baza.sale`), `migrate-legacy-leads.command.ts` (импорт из файла,
  dry-run, отчёт, повтор по `(organizationId, legacyId)`).
- **Поля старых id (11.09).** `legacyId` у Identity, Organization, Development,
  Building, Unit, Listing. Уникальность:
  - Identity, Organization, Listing — глобальная (`sparse`): у Identity и
    Organization нет organizationId, у Listing скоуп — discriminated union;
  - Development, Building, Unit — внутри организации, частичный индекс
    `legacyId: {$exists: true}`, а не `sparse`: составной sparse-индекс
    индексировал бы каждый документ без поля и падал на втором (та же ловушка,
    что описана в `lead.schema.ts`).
  Записывать эти поля пока нечему — импортёров нет.
- **Вход по паролю старой системы (11.09).** `Identity.legacyPasswordHash`
  (`select: false`). Если у Identity нет argon2-хеша, но есть старый,
  `verifyCredentials` проверяет его bcrypt-ом и при успехе перехеширует пароль в
  argon2, старое поле удаляется. Перехеш — CAS по наличию старого поля: пароль,
  сменённый параллельно, не затирается. Хеш другого формата даёт «неверный
  логин или пароль», а не 500. Работает только для Identity, которым импорт
  запишет `legacyPasswordHash`.

## Предположения, которые надо проверить на копии

1. **Старая система хеширует пароли bcrypt.** Нигде в репозиториях и
   документах это не подтверждено: алгоритм выбран по плану переезда (§8.4,
   вариант «legacy verifier»). Проверка — посмотреть префикс хешей в копии
   (`$2a$`/`$2b$`/`$2y$` — bcrypt, работает; иначе verifier заменить). Нужен
   только формат, сами хеши и пароли в переписку не передавать.
2. **Имена старых моделей** в комментариях схем (`Estate`, `EstateBuilding`,
   `EstateNewconstructionsApartment`, `EstateApartment`) и «две коллекции
   пользователей (platform и CRM)» ничем в репозитории не подтверждены.
3. **Один `legacyId` на Identity.** Если человек есть в обеих старых коллекциях
   пользователей, одного поля мало: понадобится таблица соответствия
   `источник + коллекция + старый id → новый id` (план, §8.2, MIG-02). Решать по
   реальным данным.

## Что нужно, чтобы продолжить

От владельца или IT старой системы:

- **Копия старой базы** (`mongodump`, все базы, за которыми стоят
  `api.baza.sale` и `api-crm.baza.sale`) — без неё импортёры писать не по чему.
  Передать файлом, не через репозиторий: он публичный.
- Формат хешей паролей (см. выше) — виден в копии.

Дальше по порядку плана: инвентаризация коллекций и полей (MIG-01), таблица
соответствия id (MIG-02), импорт пользователей, организаций и должностей
(MIG-03), затем ЖК, юниты и объявления (MIG-04), файлы (MIG-05). После переноса
организаций — `grants:backfill-defaults` ([default-grants-backfill](default-grants-backfill.md))
и совместимость старых адресов (N-04).
