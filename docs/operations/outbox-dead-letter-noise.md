# Семь типов событий уходили прямо в dead_letter

Статус: fixed (01.09.2026)

## Что было сломано

`OutboxPollerService`, не найдя handler'а для типа события, **не делает ни одной попытки
обработки** — он сразу выставляет `attempts = MAX_ATTEMPTS`:

```ts
const handler = this.handlerRegistry.resolve(event.eventType);
if (!handler) {
  await this.outboxEventRepository.markFailedAttempt(event._id, MAX_ATTEMPTS);
  return;
}
```

Это осознанное решение (иначе событие висело бы в `processing` вечно), но у него есть следствие:
**незарегистрированный тип = гарантированная строка в dead_letter на каждую публикацию.**

Сверка показала, что обработчиков нет у семи публикуемых типов:

| Событие | Где публикуется |
|---|---|
| `TaskCreated`, `TaskCompleted`, `TaskReassigned` | CRM, при обычной работе с задачами |
| `UnitPriceChanged`, `UnitStatusChanged` | Developments, при правке цен и статусов юнитов |
| `PositionVacated` | Organizations, при освобождении позиции |
| `UnpublicationRequested` | Publication, при снятии с публикации |

Зарегистрировано было семь обработчиков (`MediaVerified`, `PositionOccupantAssigned`,
`PublicationRequested`, четыре booking-события) — ровно столько же, сколько типов осталось без них.

## Чем это вредно

Функциональность при этом **не ломалась**: проверил каждый случай отдельно.

- Снятие с публикации отрабатывает синхронно (`publicationRepository.unpublish` в той же
  транзакции), событие — дополнительное.
- Цены юнитов в витрину маркетплейса не попадают вообще: `priceFrom` намеренно исключён из
  проекции, воркер не имеет доступа к иерархии Building/Floor/Unit (см. докстринг
  `development-publication.mapper.ts`). Устаревших цен на публичном сайте нет.

Вред в другом: **dead_letter переставал быть сигналом**. Очередь наполнялась при рутинной работе —
каждая созданная задача, каждая правка цены — и настоящая поломка (например провал
`PublicationRequested`) утонула бы в этом шуме. Та же болезнь, что у гейта, который всегда красный:
на него перестают смотреть.

Правило, которое нарушалось, было уже записано в коде — в докстринге `BookingCreatedHandler`:
«событие должно быть подтверждено воркером, а не копиться в dead_letter как неизвестный тип».
Четыре booking-события ему следуют, семь других — нет.

## Что сделано

**1. `AcknowledgedEventHandler`** — один обработчик на все семь типов: логирует и подтверждает.
Не семь почти одинаковых файлов: `EventHandlerRegistry` допускает один экземпляр под разными
ключами, а различающийся текст берётся из самого события. Существующие booking-обработчики
намеренно оставлены отдельными классами — они первыми обрастут реальной логикой.

Список типов вынесен в экспортируемую константу `ACKNOWLEDGED_ONLY_EVENT_TYPES`. Появится
настоящий побочный эффект — тип переезжает в собственный handler и убирается из списка.

**2. Страж** `apps/worker/src/outbox/handlers-coverage.spec.ts` — сверяет опубликованные и
зарегистрированные типы:

- каждое публикуемое событие имеет handler (иначе оно сразу уходит в dead_letter);
- в списке «подтверждаем без эффекта» нет типов, которые нигде не публикуются — список не
  протухает;
- сверка вообще что-то нашла — защита от молчаливо сломанного разбора.

Спеки из сверки исключены намеренно: в них есть выдуманные `TestEvent`/`UnknownEvent`, которыми
как раз проверяется поведение поллера на незнакомом событии.

Это третий такой страж после `module-boundaries` и `permission-grants`. Все три ловят один класс
ошибок: связь по строковому ключу, которую не видят ни компилятор, ни обычные тесты.

## Verification

- `handlers-coverage.spec.ts` — 3 проверки.
- `acknowledged-event.handler.spec.ts` — 4 теста: подтверждение без ошибки, обработка всех типов
  одним экземпляром, регистрация одного экземпляра под всеми ключами без конфликта дублей,
  отсутствие повторов в списке (иначе `register()` бросит на второй регистрации).
- Воркер целиком: 80 тестов, typecheck и lint чисты.
