# Вложения задачи — файлы, а не имена файлов

Статус: сделано (02.09.2026)

Четвёртый вердикт [аудита границы «экран — спецификация»](../architecture/screen-as-spec-boundary-audit-2026-09-02.md)
и самый крупный: `attachmentFileNames` хранил имена без файлов. Легаси-тип
клиента называл это честно — «демо, без загрузки на сервер», — форма брала у
`<input type="file">` только имена и выбрасывала тела, а сервер сохранял строки.
Экран обещал вложения, сервер хранил подписи к ним.

## Что стало

| Слой | Было | Стало |
| --- | --- | --- |
| Хранение | `attachmentFileNames: string[]` | `attachments: [{ assetId → MediaAsset, fileName }]` — по образцу `avatarAssetId` позиции |
| Загрузка | не было | `POST /media/upload-intent` с `purpose: task_attachment` → PUT в хранилище → `confirm`; в задачу уходят только ссылки |
| Проверка на сервере | не было | каждый asset обязан принадлежать организации и быть `verified`; чужой — 404, неподтверждённый — 400 |
| Контракт чтения | `attachmentFileNames` | без изменений: имена выводятся из `attachments`, плюс сами ссылки |
| Форма | имена в состоянии | файлы в состоянии; загрузка перед созданием; сбой любого файла — отказ формы |

Бакет для `task_attachment` — приватный: вложение задачи это внутренний
документ организации, не публичное фото.

## Почему имя живёт на связи, а не на asset'е

`MediaAsset` хранит путь, тип, размер и статус — у него нет имени файла, и
добавлять его туда значило бы менять общий пакет `media-storage` ради одного
потребителя. Имя — это подпись, которую человек видел при выборе, того же рода,
что `alt` у медиа объекта недвижимости; ему место на связи «задача → файл».

## Почему форма грузит до создания, а не после

Сервер отклоняет ссылку на файл, которого нет или который не подтверждён. Значит
порядок один: сначала файлы, потом задача. Сбой любого файла — отказ с его
именем, а не задача «с вложением», которого не существует: это тот же класс
лжи, что имена без файлов, только созданный заново.

## Что это открывает и чего не даёт

Открывает: экран показывает «N файл(ов)» по настоящим файлам, и файл можно
будет отдать — asset лежит в хранилище.

Открывает (11.09.2026): ~~скачать вложение из карточки нельзя~~ — закрыто
для задач. `GET /tasks/:taskId/attachments/:assetId/download` отдаёт
`{url, fileName}` — `url` подписанная GET-ссылка на 5 минут
(`MediaStorageService.createDownloadUrl`, примитив уже существовал, вызывать
было неоткуда), `fileName` берётся со связи задача → файл, не с asset'а.
Проверка — та же, что у самой задачи: `getTaskAttachmentDownloadUrl`
переиспользует `getTask` целиком (tenant/own/personal-scope), затем сверяет
`assetId` со списком `task.attachments` — asset, реально существующий и
подтверждённый, но не привязанный к ЭТОЙ задаче, тоже 404, не только чужой
организации. У `agency_document` такого эндпоинта по-прежнему нет — доку
там просил разбираться отдельно, общий механизм (сама подписанная ссылка)
теперь есть, вызывающий код под конкретный документ — нет.

Допустимые типы — `image/*` и `application/pdf` (`ALLOWED_MIME_TYPES`): DOCX и
XLSX загрузить нельзя. Ограничение медиа-модуля, не вложений; расширять — там.

## Проверено

- unit API: 806;
- интеграционные: полный набор 430 (в задачах +4: ссылка на подтверждённый
  asset с выводом имён, неподтверждённый — 400, чужой организации — 404, имена
  без файлов — 400);
- клиент: 227 (+3 загрузка: три шага по порядку, отказ хранилища, отклонённый
  файл; +3 форма: задача получает ссылку, сбой блокирует создание, без файлов
  загрузка не вызывается; +1 маппер).

Четыре диверсии, все ловятся: сервер принимает неподтверждённый asset; сервер
принимает asset чужой организации; форма создаёт задачу, не дожидаясь
загрузки; клиент считает отклонённый файл загруженным.

**Одна оговорка.** Первый полный прогон интеграционного набора дал 1 упавший
тест из 430, повтор — 430 из 430. Какой именно — установить не удалось: мой же
`grep` в фоновой команде обрезал лог до итоговой строки. В наборе есть
нестабильный тест, и он пока не назван; при следующем падении лог сохранять
целиком.
