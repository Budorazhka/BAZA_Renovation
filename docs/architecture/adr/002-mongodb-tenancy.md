# ADR-002: MongoDB multi-tenancy через обязательный organizationId + TenantContext

**Статус**: Proposed
**Дата**: 25.08.2026

## Context

ERP multi-tenant — Accepted decision, неизменяемое (master plan разд.2.2, разд.5.4). Организации (агентство/застройщик/независимый риэлтор) не должны видеть данные друг друга. Нужно выбрать конкретный механизм изоляции на уровне MongoDB, поскольку "multi-tenant" как формулировка не определяет реализацию (варианты: database-per-tenant, collection-per-tenant, shared collection с tenant-полем).

`[owner decision — xlsx]`, вопрос #27/#28: владелец подтвердил, что изоляция интуитивно понятна (лиды/акции закрыты между организациями, шахматка публична), но резко раскритиковал попытку уточнить вопрос как избыточную — то есть сама концепция tenant isolation не требует продуктового уточнения, только инженерной реализации.

## Decision

**Shared collections + обязательное поле `organizationId` на каждом ERP-tenant-scoped документе + принудительный `TenantContext`, создаваемый исключительно сервером и enforced на уровне repository layer, а не только типов.**

TypeScript-типизация делает пропуск TenantContext неудобным на этапе написания кода, но **не является гарантией безопасности сама по себе** — типы проверяются на compile-time и ничего не проверяют в runtime; недисциплинированный или скомпрометированный код может обойти типовую проверку (например, через `as any`, динамический вызов, или баг в самой repository-реализации). Реальная защита строится на следующих независимых, runtime-enforced механизмах:

1. **`TenantContext` создаётся только сервером**, никогда не принимается от клиента. Middleware/guard на уровне API извлекает `organizationId` и `positionId` из серверной сессии (после проверки токена) и из актуального membership (активный `PositionAssignment` этой identity в этой organization на момент запроса) — **не из body, query, path-параметра или заголовка запроса**. Любое поле `organizationId`, присланное клиентом в теле запроса, игнорируется при построении TenantContext и используется (если вообще нужно) только как *значение бизнес-данных* (например, при явной админской фильтрации), никогда как источник scope текущего запроса.
2. **Прямой доступ к Mongoose-моделям закрыт вне repository layer.** Domain-модули (сервисы, контроллеры, command/query handlers) не импортируют Mongoose-модели напрямую и не строят произвольные `Model.find(...)` — единственная точка доступа к MongoDB для tenant-коллекций — repository-класс модуля. Это enforced архитектурным dependency-тестом (тот же механизм, что в C-03 module boundary test): импорт `mongoose.Model`/сырых схем за пределами `*/repository/*` — ошибка сборки.
3. **Repository автоматически добавляет tenant-фильтр**, не полагаясь на то, что вызывающий код передал корректный `organizationId` в query-объект вручную. Каждый tenant-repository оборачивает низкоуровневый Mongoose-вызов так, что `{organizationId: ctx.organizationId}` инжектируется в фильтр запроса самим repository-методом на основе полученного `TenantContext`, а не собирается вызывающей стороной построчно — единая точка внедрения фильтра, не N точек, где легко забыть один.
4. **Обязательный tenant escape test suite** (release gate, уже зафиксирован в QA-002/SEC-001 traceability): для каждого repository-метода — попытка передать `TenantContext` от организации A и получить/изменить/удалить запись организации B должна детерминированно завершаться отказом (без раскрытия факта существования записи), проверяется автоматическим тестом в CI, не только code review.
5. **Worker-задачи безопасно восстанавливают контекст, с обязательной ревалидацией для user-initiated заданий.** Фоновые задания (ADR-001) не наследуют HTTP-сессию напрямую — при постановке в очередь API-процесс сериализует **уже провалидированный** `TenantContext` (или его достаточный слепок — `organizationId` + `positionId`, не сырые токены) в payload задания. Два разных класса заданий обрабатываются по-разному:
   - **User-initiated задания** (инициированы конкретным действием сотрудника — например, ручной пересчёт индекса, экспорт по запросу менеджера): перед выполнением worker **повторно проверяет**, что `PositionAssignment`, зафиксированный в payload на момент постановки, всё ещё активен и обладает нужным правом (запрос к Organizations/Authorization модулю по актуальному состоянию, не доверие к слепку из payload как к финальной истине). Если за время нахождения задания в очереди доступ был отозван (увольнение, блокировка, revoke permission) — **задание отменяется**, не выполняется, событие отмены пишется в audit.
   - **Системные задания** (не инициированы конкретным человеком в моменте — истечение брони по таймеру, плановая проверка актуальности, scheduled cleanup): выполняются **под отдельным системным actor** (`system` identity, зарезервированный, не привязанный к PositionAssignment конкретного человека), не требуют ревалидации чьих-либо прав, поскольку не действуют от чьего-либо имени — их легитимность определяется самим фактом наступления системного условия (таймер истёк), а не полномочиями инициатора. Audit-запись такого события отражает `actor: system`, не подставного человека.
6. **Admin доступ к tenant-данным идёт НЕ через отсутствие organizationId-фильтра**, а через полностью отдельный `AdminContext` (permission + scope + причина + audit event) — Admin-repository-методы физически отдельные от ERP-tenant-repository методов, не bypass/условный флаг в одном и том же коде.

### Scope: где `organizationId` обязателен, а где нет

Не каждая сущность в системе принадлежит ERP-организации — это прямое следствие уже принятого правила «Marketplace-аккаунт возможен без ERP» (Неизменяемые решения, CLAUDE_HANDOFF_TZ.md разд.5). Формулировка выше ошибочно подразумевала универсальный обязательный `organizationId`; уточнение:

- **`Organization`** — сама сущность организации не имеет `organizationId` (она и есть корень tenant-границы, не tenant-scoped документ внутри себя).
- **`Identity`** — представляет физического человека, не принадлежит организации напрямую; связь человека с организацией идёт через `PositionAssignment` → `Position` → `Organization`, причём один Identity может со временем занимать позиции в разных организациях последовательно (не одновременно, IAM-003), но сам объект Identity не хранит текущий `organizationId` как постоянное поле.
- **`PropertyAsset`/`Listing`, созданные независимым marketplace-пользователем без ERP-организации** (обычный собственник, продающий одну квартиру — подтверждённый сценарий, master plan разд.2.3), **не обязаны иметь `organizationId`**. Вместо этого вводится явное поле **`publisherScope`**: `{ type: 'organization', organizationId: ObjectId } | { type: 'marketplace_account', identityId: ObjectId }`. Repository-слой и TenantContext-enforcement для таких объектов проверяют владение через `publisherScope`, не через жёстко обязательный `organizationId` — если объект связан с организацией (риэлтор внутри агентства опубликовал через свою organization), используется organization-ветка; если это независимый marketplace-аккаунт — используется identity-ветка с отдельным, более простым access-контролем (владелец = единственный, кто может редактировать/снимать с публикации свой объект, без командной иерархии Position/Assignment).
- Все явно ERP-native сущности (Position, PositionAssignment, Contact, Lead, Task, Deal, Booking внутри организации, Selection, созданный сотрудником организации) — `organizationId` обязателен, как в исходной формулировке.
- Публичные read-model сущности (`MarketplacePublication`, публичный профиль риэлтора/агентства) не используют `organizationId` как ограничитель видимости вообще — они спроектированы отдельно как публичные проекции (ADR-005), не защищаются TenantContext-механизмом этого ADR.

## Alternatives considered

**Database-per-tenant** (каждая организация — своя MongoDB database). Отклонено: при целевом масштабе (до сотен организаций в перспективе) создаёт линейно растущее число баз данных, усложняет backup/restore (per-DB вместо единого), усложняет cross-tenant admin-запросы (агрегация по городу/домену для Admin-аналитики требует federated query вместо простого `$match`), не даёт реальных преимуществ изоляции при корректной реализации TenantContext на уровне кода.

**Collection-per-tenant** (например, `leads_org123`, `leads_org456`). Отклонено: MongoDB не оптимизирована под тысячи мелких коллекций, схема/индексы дублируются по каждой коллекции вместо единого определения, миграции индексов должны применяться к каждой коллекции отдельно — операционная сложность без выигрыша в изоляции по сравнению с полем + индексом.

**Изоляция только на уровне application-layer без обязательности в типах** (просто "не забывать" добавлять фильтр по organizationId в каждый query). Отклонено явно и жёстко: это ровно тот паттерн, который master plan запрещает («Не делать запрос tenant-данных без явного TenantContext», разд.12.5) — человеческая ошибка в одном месте кода = полный tenant escape, что является top-priority security risk (SEC-001 в traceability matrix, tenant escape test suite — обязательный release gate).

## Consequences

**Positive**:
- Один набор индексов/схем на коллекцию, простое резервное копирование (весь backup — одна операция на всю БД).
- Cross-tenant admin-агрегация (аналитика по городу, поиск по домену) — обычный MongoDB query с `$match` по нужным условиям, не federated query.
- Единая точка внедрения tenant-фильтра (repository layer) даёт один аудируемый механизм защиты вместо N мест, где вызывающий код мог бы забыть фильтр.

**Negative**:
- Требует дисциплины на этапе C-03 (API skeleton): каждый новый tenant-модуль обязан спроектировать repository interface с server-side TenantContext и dependency-тестом на прямой доступ к моделям с первого коммита, не добавлять постфактум.
- `publisherScope`-ветвление (organization vs marketplace_account) добавляет реальную инженерную сложность в repository-слой PropertyAsset/Listing — два разных access-control пути на одной коллекции должны быть спроектированы и протестированы одинаково строго, не только «основной» organization-путь.
- Worker context restoration требует отдельного сериализуемого формата TenantContext, который переживает переход через очередь (Redis/BullMQ) без потери гарантий — ошибка здесь (например, доверие к organizationId из тела задания без сверки с тем, что провалидировал API) сводит на нет всю защиту API-слоя.
- Один "shared" collection на большом масштабе может потребовать sharding по `organizationId` в будущем (не требуется на целевых 40 пользователях/MVP).
- Compound-индексы с `organizationId` первым полем немного больше по объёму, чем индексы без tenant-префикса — незначительно на целевом масштабе.

## Security impact

Это прямая митигация главного риска threat model (tenant escape/IDOR — первый пункт в перечне threat model master plan разд.6.7). Защита строится на пяти независимых runtime-механизмах (см. Decision выше: server-only TenantContext, закрытый прямой доступ к моделям, repository auto-filter, worker context restoration, отдельный AdminContext), не на одной типовой проверке. Обязательный тест: tenant escape suite (release gate C-10) — попытки cross-org read/update/list/search/export через все repository-методы (включая методы с `publisherScope`-ветвлением) должны быть denied, без раскрытия факта существования записи другой организации (не 403 с деталями, а 404-подобное поведение, скрывающее существование). Отдельно тестируется: попытка передать `organizationId` в теле/query клиентского запроса, отличный от реального membership — должна игнорироваться сервером, не приводить к смене эффективного tenant scope.

## Operational impact

Индексы с `organizationId` первым полем должны быть частью каждой миграции с первого дня — ретроактивное добавление на заполненной коллекции требует `background: true` построения индекса без блокировки записи (стандартная MongoDB-практика, но должна быть явно прописана в runbook C-02).

## Rollback / revisit trigger

Пересмотреть при:
- Регуляторном требовании физической изоляции данных по организациям (например, если конкретный крупный клиент потребует отдельную инфраструктуру по контракту) — тогда мигрировать конкретно эту организацию в отдельную БД, не менять модель для всех.
- Достижении масштаба, при котором sharding по `organizationId` становится необходимым — на этом этапе схема (organizationId как shard key) уже совместима, миграция на sharded cluster не требует смены модели данных.
