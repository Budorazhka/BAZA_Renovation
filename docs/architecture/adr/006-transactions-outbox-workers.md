# ADR-006: MongoDB transactions + transactional outbox + idempotent workers

**Статус**: Accepted (Idempotency-Key механизм реализован 26.08.2026 — см. `docs/operations/adr006-idempotency-key.md`; BookingLock/transactional outbox/worker deduplication применены на publishDevelopment/assignOccupant/uploadAvatar и др., Booking-модуль сам ещё не реализован)
**Дата**: 25.08.2026

## Context

`[owner decision]`, master plan разд.6.4/2.4: бронирование одного юнита должно атомарно исключать пересекающиеся активные брони, «защита транзакцией/lock record, не UI-проверкой» (явно прописано как требование, не предложение). Публикация (ADR-005), назначение позиции (ADR-003), критические биллинговые операции — все требуют атомарности "изменить состояние + гарантированно уведомить об этом остальную систему".

Прямая зависимость от ADR-001: MongoDB transactions требуют replica set даже на одном физическом узле — уже зафиксировано как инфраструктурная предпосылка.

`[owner decision — xlsx]`, вопрос #117 (атомарная блокировка): «не понимаю че это значит. Может быть бронь 1го на разные дату и время. Разными лидами» — владелец делегировал техническую реализацию, подтвердив только бизнес-факт "конфликт возможен", не зная деталей защиты.

## Decision

**Внутри одного бизнес-действия используется MongoDB multi-document transaction, с явной точкой сериализации через lock-документ — не только snapshot-изоляция транзакции сама по себе.** MongoDB transactions по умолчанию используют snapshot read concern: два конкурентных `book()`-вызова, стартовавшие до коммита друг друга, оба могут прочитать "конфликтов нет" в своём снепшоте и оба попытаться создать непересекающуюся, с их собственной точки зрения, бронь — простое "прочитать существующие брони, затем записать новую" внутри транзакции **не гарантирует** отсутствие overlap само по себе, если нет общей точки, на которой конкурентные транзакции гарантированно столкнутся.

Эта точка — отдельный документ **`BookingLock`** (коллекция `booking_locks`, `_id: unitId`, `updatedAt`, `currentVersion` — по одному документу на unit, не на каждую попытку брони). Порядок операций внутри транзакции `book(unitId, dates)`:
1. **Записать (upsert / findOneAndUpdate с инкрементом версии) `BookingLock` по `_id: unitId` первым действием транзакции** — это гарантированно создаёт write conflict между двумя конкурентными транзакциями на один и тот же `unitId`: MongoDB откатывает (`TransientTransactionError`) вторую из двух конкурентных транзакций, пытающихся записать в один и тот же документ, до того как обе успеют независимо решить "конфликтов нет". Проигравшая транзакция ретраится (стандартный retry-loop для MongoDB transactions), при повторной попытке видит уже закоммиченное состояние первой.
2. **Только после успешной записи `BookingLock`** — проверка отсутствия пересекающихся активных броней (запрос по partial index на активные брони по `unitId`+`dateRange`), в рамках той же уже сериализованной относительно других booking-транзакций на этот unit транзакции.
3. Если конфликт дат найден — транзакция откатывается целиком (несмотря на уже произведённую запись `BookingLock` — откат транзакции откатывает все её операции, включая lock-запись).
4. Если конфликта нет — создаётся запись `Booking`, пишется outbox-событие `BookingCreated`, транзакция коммитится.

`BookingLock` не хранит сами данные о занятости (это делает Booking-коллекция и partial index на ней) — его единственная роль — быть гарантированной точкой сериализации per-unit, превращающей "оптимистичную" snapshot-транзакцию в фактически последовательную обработку конкурентных попыток брони одного и того же юнита.

**Transactional outbox pattern**: после успешной бизнес-транзакции событие пишется в `outbox_events`-коллекцию **в той же транзакции**, не отдельным вызовом после коммита. Структура: `{_id, eventType, payload, aggregateId, aggregateType, createdAt, processedAt: null, deduplicationKey, attempts: 0, status: 'pending' | 'processing' | 'done' | 'dead_letter'}`. Это устраняет классическую проблему "бизнес-изменение прошло, но уведомление потерялось из-за сбоя между коммитом и постановкой в очередь" — если транзакция закоммичена, событие гарантированно есть в базе; если транзакция откатилась, события тоже нет.

**Worker вычитывает outbox** через change stream (MongoDB change streams на `outbox_events`, доступны благодаря replica set — та же инфраструктурная предпосылка ADR-001) или polling с коротким интервалом (fallback, если change streams создают операционную сложность на старте — решается на C-02/C-08 по факту). При успешной обработке помечает `processedAt`+`status: 'done'`. При ошибке — увеличивает `attempts`, применяет exponential backoff, после N попыток переводит в `dead_letter` (требует ручного разбора, не теряется молча).

**Идемпотентность worker'а через `deduplicationKey`**: каждое outbox-событие несёт детерминированный ключ (например, для `BookingCreated` — `booking:{bookingId}:created`), worker перед выполнением side-effect проверяет, не был ли этот ключ уже обработан (отдельная `processed_keys`-коллекция с TTL, или проверка на идемпотентность самой side-effect операции — например, upsert публикации по `sourceId`+`sourceType`, ADR-005, естественно идемпотентен без доп. проверки). Replay одного и того же события (намеренный или из-за retry) не создаёт дублирующийся side-effect (второе уведомление, второй лид, дублирующаяся публикация).

**Idempotency key для клиентских критических команд**: `publish`, `book`, `cancel`, manual ledger operations принимают клиентский `Idempotency-Key` header (UUID, сгенерированный клиентом при первой попытке). Это отдельный механизм от worker deduplication — защищает от дублирования на уровне API-вызова, до того как транзакция вообще началась.

Хранение — отдельная коллекция `idempotency_records`: `{identityId, operation, key, requestHash, response: {status, body}, createdAt}`. **Уникальный индекс на `{identityId: 1, operation: 1, key: 1}`** — ключ scoped к конкретному пользователю и конкретной операции, не глобально уникален сам по себе: два разных identity технически могут прислать одинаковый UUID без коллизии (крайне маловероятно, но не полагается на глобальную уникальность клиентского UUID как единственную защиту), а один и тот же identity не может случайно переиспользовать ключ между разными операциями (`book` и `cancel` с одним и тем же key — разные записи, не конфликт).

Обработка запроса с уже существующим `{identityId, operation, key}`:
- Если `requestHash` (детерминированный хеш тела запроса) **совпадает** с сохранённым — это подтверждённый retry того же запроса, возвращается **сохранённый `response`** без повторного выполнения операции (тот же HTTP-статус и тело, что при первом успешном выполнении, включая случай, когда первая попытка вернула ошибку — идемпотентность касается и неуспешных ответов, не только успешных).
- Если `requestHash` **не совпадает** — клиент прислал тот же `Idempotency-Key`, но другое тело запроса (ошибка клиента или попытка обхода) — запрос **отклоняется** с явной ошибкой конфликта (409), не выполняется и не подменяет сохранённый response.

Запись в `idempotency_records` создаётся **в той же транзакции**, что и сама бизнес-операция (booking-транзакция, публикация и т.д.) — тот же transactional outbox принцип: если бизнес-транзакция закоммичена, idempotency-запись гарантированно есть; если откатилась, записи тоже нет, и повторная попытка с тем же ключом обрабатывается как первая, не как retry несуществующего успеха.

## Alternatives considered

**Two-phase commit между отдельными коллекциями без MongoDB transactions** (application-level saga с компенсирующими действиями). Отклонено: при modular monolith (ADR-001) с единой БД нет необходимости в распределённой саге — MongoDB transactions решают ту же задачу нативно и проще, saga-паттерн оправдан только при реальной распределённости данных между независимыми хранилищами, чего здесь нет.

**Publish события напрямую в Redis/BullMQ без outbox-таблицы** (API сразу после бизнес-транзакции кладёт задание в очередь отдельным вызовом). Отклонено: создаёт окно между коммитом бизнес-транзакции и постановкой в очередь, где процесс может упасть (например, между строкой "commit transaction" и строкой "queue.add()") — бизнес-изменение произошло, но никто об этом не узнает, воркер никогда не запустится. Outbox устраняет это окно архитектурно, ценой одной дополнительной коллекции и polling/change-stream механизма.

**UI-level проверка бронирования** (клиент проверяет доступность перед отправкой формы, сервер доверяет). Отклонено явно и жёстко — прямо запрещено владельцем формулировкой «защита транзакцией/lock record, не UI-проверкой» — классический race condition при двух одновременных пользователях, UI-проверка не защищает от параллельных запросов.

## Consequences

**Positive**: гарантия "at-least-once delivery с идемпотентной обработкой" для всех критичных side-effects (уведомления, публикации, индексация) без сложной distributed-транзакционной инфраструктуры. Booking conflict физически невозможен на уровне БД, не полагается на дисциплину application-кода.

**Negative**: каждая команда, требующая outbox-событие, немного сложнее в реализации, чем "просто сохранить документ" — разработчик обязан помнить о паттерне outbox+idempotency для каждой новой критической команды (митигируется через shared helper/decorator на уровне NestJS command handler, стандартизирующий паттерн, не оставляющий его "на память"). Change streams (если выбраны как механизм вычитывания outbox) требуют replica set с oplog достаточного размера — операционная деталь, которую нужно учесть в infrastructure-спецификации.

## Security impact

Косвенная защита: booking race condition — один из пунктов threat model (master plan разд.6.7, "booking race" явно перечислен). Idempotency key также защищает от намеренного replay-атаки на критические команды (повторная отправка перехваченного/повторно воспроизведённого запроса publish/book не создаёт дублирующийся эффект).

## Operational impact

`outbox_events` коллекция требует TTL-политики на `status: 'done'` записи (не расти неограниченно — например, 30 дней хранения обработанных событий для отладки/аудита, затем автоочистка). `dead_letter`-записи требуют dashboard/алертинга для ручного разбора (часть observability C-02, не откладывается до продакшена — на MVP-масштабе может быть простой периодической проверкой, не полноценным alerting-стеком, соответствует "MVP не production-grade" контексту budget-решения).

## Rollback / revisit trigger

Пересмотреть механизм вычитывания outbox (change streams → dedicated message broker вроде Kafka/RabbitMQ) при масштабе, на котором MongoDB change streams перестают справляться с объёмом событий, или при появлении требования на cross-service event distribution за пределами одного monolith-процесса (то есть при пересмотре ADR-001 в сторону выделения сервисов).
